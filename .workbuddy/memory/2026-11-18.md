## 架构要点
- `HookPoint` 枚举 = 14 个 API 点，`AdaptProgress` 记 PENDING/RUNNING/OK/MISS/DISABLED/FAIL
- 两阶段适配：`onPackageLoaded`（default loader）→ `onPackageReady`（app loader 重试）
- 适配缓存：指纹 = 包名+versionCode+versionName+lastUpdateTime+模块versionCode+`Anchor.ANCHOR_REV`，
  存目标 app 自己的 `files/nnnhook/adapt.txt`，命中则跳过 DexKit，按 `类名|方法名|参数表` 反射还原 Method
- 弹窗：挂 framework `Activity.onCreate`，首个界面弹非全屏 AlertDialog（Application context 弹 Dialog 会 BadToken）
- Android 14+ 禁止从可写目录 DexClassLoader（`Writable dex file is not allowed`）→ 自检走 `DexSource.fromApk` 拆 dex + `DexKitBridge.create(byte[][])`
- `module.prop` 用 modern API 字段（minApiVersion/targetApiVersion/staticScope/exceptionMode/autoHotReload）；
  **`META-INF/xposed/java_init.list` 不能删**，删了框架找不到 XposedModule 子类；模块名取 `android:label`、描述取 `android:description`

1. 配置键 `dialog_filters_limit_*` / `pinned_dialogs_count_max_*` 在 dex 里 **fieldDef=0、fieldRef=0**，

   `dialogFiltersLimitPremium=30`、`savedDialogsPinnedLimitPremium=100`、
   `maxFolderPinnedDialogsCountPremium=100`、`topicsPinnedLimit=5`
3. `MessagesController`（混淆名 `s6`，333 方法 / 147 个 int 字段）的 `#引导尼古丁之力(int)`

### 三条错路（都验证过）
- 直接改 `mainconfig.xml` → 启动后被服务端 config 重写（改完重启变回 30）
- 在 loadConfig **之前**改字段 → 方法内部重新赋值（1000 被打回 30）

### 最终方案
hook loadConfig，**proceed 返回之后**按值抬升（UI 读内存字段，不读 prefs）：
- 值 == 30 → 2 个字段（文件夹上限）
- 值 == 100 → 11 个字段（置顶 + chatlistInvites/quickReplies 等同族上限）
- 全部抬到 1000，日志 `raised N field(s)` + 逐字段 `30 -> 1000`
- 缓存命中模式同样生效（loader 落点已纳入缓存 spec，前缀 `loader|`）

### 教训
缓存必须覆盖**所有**落点类型，漏一类该功能在缓存模式下静默失效（loader 就踩过这个坑）。

## 第七轮：双击跳未读——滚动打通（2026-11-18 15:10）
卡了很久的"滚动"终于通了，关键是**按签名找方法，不按名字找**。

### 根因
`eu.layoutManager`（`org.telegram.ui.gr`）的父类是
`androidx/recyclerview/widget/引导尼古丁之力` —— **androidx 的类本身也被 R8 混淆了**。
所以 `scrollToPositionWithOffset` 这个名字根本不存在，它被改名成
`假烟发现就跑路(int, int)`。

### 正确解法
```java
Object lm = readField(layout, "layoutManager");
for (Method m : lm.getClass().getMethods()) {
    Class<?>[] ps = m.getParameterTypes();
    if (ps.length == 2 && ps[0] == int.class && ps[1] == int.class
            && m.getReturnType() == void.class) {
        m.invoke(lm, index, 0);   // == scrollToPositionWithOffset(index, 0)
        return;
    }
}
```
日志证据：`scrolled via layoutManager.假烟发现就跑路(int,int) → 0`

### 数据层的坑（已修）
`itemInternals` 的下标**不等于**列表位置（里面混了分组标题/提示条），
必须只对"真正带 TLRPC$Dialog 的项"递增计数：
```java
int pos = 0;
for (Object item : list) {
    Object dialog = findFieldOfType(item, "TLRPC$TLRPC$Dialog");
    if (dialog == null) continue;          // 非会话项，不占位置
    if (unread > 0 && !silent) return pos;
    pos++;
}
```

## 第八轮：双击跳未读——定位逻辑最终确认（2026-11-18 15:38）
用户反馈"双击跳到顶部，但未读不在顶部"。逐层排查后确认**逻辑是对的**，是数据呈现造成的误解。

### 一路排掉的干扰
1. `itemInternals` 下标 vs 列表位置：`viewType` 全 0、`order` 全 0（服务端没下发），
   自己按 order/date 重排反而更乱 → 最终确认 **itemInternals 的顺序就是 adapter 的显示顺序**，直接用下标。
2. `folder_id` 过滤：加上（避免跨分组串味），实测"所有聊天"下 folderId=0 不筛任何东西。
3. `dialog.pinned` / `last_message.date`：置顶和时间都试过，同一秒多条消息无法区分 → 放弃重排。

### 决定性验证
日志 `first unread rank=0 unread=2085 id=-4351481968` 与截图对比：
列表第一条 Bettbox Chat 显示 2089（4 秒内又进 4 条）→ **item[0] 确实是列表第一条**。

### 所以"总是滚到顶部"不是 bug
`rank=0` 意味着"列表最顶部那条就是最新未读"，滚到顶部是正确的。
用户感觉"没跳到未读"，是因为顶部那条本身就有未读（活跃群多，顶部几乎总有未读）。

### 排查方法论（重要）
- 活跃群数据秒级变化，dump 与截图必不是同一时刻，对比会差几条 —— 别误判成偏移
- `visiblePosOf`（用 dialog.id 匹配 currentDialogId）能确认"目标是否已在屏幕上"
- `adapter.itemInternals` 是唯一拿得到的数据源；`getItem/getItemCount` 名字被换成中文，

### 这个功能为什么没做成（留给以后）
滚动 API **是通的**（实测列表从 9527bot 跳回 zen/adzen，截图证实），
卡在**拿不到真实 adapter position**：
- `itemInternals` 的下标 ≠ 列表显示位置（实测偏 2~3 条，新消息刷进来时更乱）
- `RecyclerView.getChildAdapterPosition(View)` —— androidx 也被 R8 混淆，名字没了
- `LayoutManager.findFirstVisibleItemPosition()` —— `gr` 上有 4 个 `()->int`，分不清哪个是它
  （按"值在 0..30"猜的那个永远返回 0）
- `adapter.getItem(pos)` —— g0 的 61 个方法里没有 `(int)->Object`
